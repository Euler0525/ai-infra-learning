# 从生成结果分歧定位到 RoPE 精度问题

本文记录一次 Qwen2.5 本地实现与 Hugging Face 基线生成结果不一致的排查过程。问题表面上表现为两个 greedy 生成器输出了不同文本，最终定位到本地 `RotaryEmbedding` 的 inverse frequency 被错误转换为 BF16。排查的思路是先找到第一个分歧 token，再沿模型执行链逐层缩小范围。

## 修复前的问题现象

排查开始时，使用相同模型、revision、prompt 和 greedy 参数分别运行：

```powershell
uv run python -m mini_llm.generate
uv run python -m mini_llm.local_generate
```

修复前，Hugging Face 基线生成了 `your lunch options`，本地模型生成了 `your lunch choices`，随后两条序列完全分叉。由于 greedy 每一步都会把上一个输出作为下一步输入，一次很小的 logits 排序变化就会影响此后的全部 token，因此不能根据最终文本差异直接判断错误发生在哪里。这里记录的是故障发生时的历史现象，不是修复后的输出。

这两个入口的主要差别如下：

| 环节 | Hugging Face 基线 | 本地模型 |
| --- | --- | --- |
| Tokenizer | Hugging Face | Hugging Face |
| 权重 | Hugging Face 加载 | 直接读取 Safetensors |
| 模型前向 | `AutoModelForCausalLM` | `Qwen2p5ForCausalLM` |
| Attention | 默认 SDPA，测试中使用 eager | 自定义 PyTorch eager |
| KV Cache | Hugging Face Cache | 自定义连续 KV Cache |
| 采样 | Greedy `argmax` | Greedy `argmax` |

## 排查过程

### 定位第一个分歧 token

首先不要比较最终文本，而应在两边使用相同前缀逐 token 执行，记录每一步的 `argmax`、top-k logits、平均误差和最大误差。两边前 18 个生成 token 完全一致，第一次实际分歧发生在第 19 个 token，共同前缀是：

```text
As an AI language model, I don't have access to real-time information about your lunch
```

此时本地模型选择 `choices`，Hugging Face 默认 SDPA 选择 `options`：

| 模型 | 候选 token | logit |
| --- | --- | ---: |
| 本地模型 | `choices` | 19.875 |
| 本地模型 | `options` | 19.750 |
| HF SDPA | `options` | 19.750 |
| HF SDPA | `choices` | 19.625 |

候选分数只相差 `0.125`。这说明问题更可能来自 BF16 数值误差，而不是明显的 mask、position 或权重映射错误。

### 固定注意力后端

检查 Hugging Face 配置后发现，`mini_llm.generate` 默认使用 `sdpa`，而真实权重测试显式使用 `eager`。SDPA 与手写 eager attention 在数学上等价，但 BF16 下的 kernel、计算顺序和舍入方式不同，遇到接近并列的 logits 时可能得到不同的 greedy token。

将 Hugging Face 后端改为 eager 后，第 19 步仍然发生分歧，不过 HF eager 选择的是 `plans`，本地模型仍选择 `choices`。这说明注意力后端不一致会干扰比较，但不是本地模型误差的唯一来源。后续排查统一使用 HF eager，确保两边具有尽可能相同的计算路径。

### 排除权重、采样和 KV Cache

为了避免在错误方向上继续排查，依次进行了以下对照实验：

| 假设 | 验证方法 | 结论 |
| --- | --- | --- |
| 权重映射错误 | 比较 Embedding、RMSNorm、Q/K/V projection 输出 | 逐元素完全相同，排除 |
| 采样实现错误 | 两边使用 `temperature=0`，直接比较 logits 和 `argmax` | 分歧在采样之前已经存在，排除 |
| KV Cache 写入或 position 错位 | 比较本地 cached decode 与完整前向重算 | 两条路径都选择 `choices`，排除 |
| 模型结构错误 | 使用 FP32 比较本地模型与 HF eager | 前 300 个生成 token 一致，未发现结构错误 |
| BF16 数值路径错误 | 逐层、逐算子比较第一次出现误差的位置 | 第一处误差出现在 RoPE |

其中 KV Cache 对照尤其重要。如果 cached decode 与完整重算结果不同，问题通常位于 cache slot、cache length、decode position 或 causal mask；这次两条本地路径得到相同 top-1，说明连续 KV Cache 不是根因。

### 逐算子定位

对第一层进行逐算子比较后得到以下结果：

| 中间结果 | 是否完全一致 |
| --- | --- |
| Token Embedding | 是 |
| Input RMSNorm | 是 |
| Q projection | 是 |
| K projection | 是 |
| V projection | 是 |
| Q RoPE | 否 |
| K RoPE | 否 |

Q RoPE 的最大误差达到 `0.25`，K RoPE 的最大误差达到 `0.578125`。因此，误差不是从 Linear、RMSNorm 或权重加载进入，而是从旋转位置编码开始。

## 根因

RoPE 使用的 inverse frequency 为：

$$
\omega_i = \theta^{-2i/d}, \qquad i = 0,1,\ldots, d/2-1
$$

位置为 $m$ 时，旋转角为 $m\omega_i$，Q/K 的旋转写作：

$$
\operatorname{RoPE}(x_m)
= x_m\cos(m\omega)
+ \operatorname{rotate\_half}(x_m)\sin(m\omega)
$$

本地实现通过 `register_buffer("inv_freq", ...)` 保存 `inv_freq`。虽然使用了 `persistent=False`，它只表示该 buffer 不写入 `state_dict`，并不阻止 `Module.to()` 转换它的 dtype。

本地模型加载时执行：

```python
model = Qwen2p5ForCausalLM(config).to(
    device=settings.device,
    dtype=settings.dtype,
)
```

当 `settings.dtype` 为 `torch.bfloat16` 时，模型参数和浮点 buffer 都被转换为 BF16。因此本地 `inv_freq` 也被量化，而 Hugging Face 的 `inv_freq` 保持 FP32。实测其中一个频率从正确的 `0.6493816376` 变为 `0.6484375`。

RoPE 的角度误差会随 position 放大，再经过 24 层传播和多步 decode 累积。最终虽然整体 logits 仍然接近，但足以改变接近并列候选的排序。

需要注意，仅在 forward 中调用 `self.inv_freq.float()` 不能修复问题。BF16 转换已经丢失了有效位，将量化后的值转回 FP32 只会改变存储格式，不会恢复原始精度。必须保留原始 FP32 值，或者根据 `base` 和 `head_dim` 重新计算。

## 修复方案

`RotaryEmbedding` 保存 `head_dim` 和 `base`，并使用明确的 FP32 计算函数创建 `inv_freq`。模块执行 `_apply` 完成 device/dtype 转换后，在目标设备上重新计算 FP32 frequency：

```python
def _make_inv_freq(
    self,
    device: torch.device | None = None,
) -> torch.Tensor:
    return 1.0 / (
        self.base ** (
            torch.arange(
                0,
                self.head_dim,
                2,
                device=device,
                dtype=torch.float32,
            ) / self.head_dim
        )
    )

def _apply(self, fn, recurse: bool = True) -> "RotaryEmbedding":
    super()._apply(fn, recurse=recurse)
    self.inv_freq = self._make_inv_freq(self.inv_freq.device)
    return self
```

这样执行 `model.to(device="cuda", dtype=torch.bfloat16)` 后，模型权重仍为 BF16，`inv_freq` 则保持 FP32。sin/cos 最终仍可以转换为 Q/K 的 dtype，不会改变模型其余部分的计算精度和显存策略。

为了使正确性基线稳定，`mini_llm.generate` 同时显式指定 `attention_implementation="eager"`。这不是生产推理必须使用 eager，而是正确性对照时必须固定后端，否则 SDPA 与自定义 eager 的 BF16 舍入差异会成为额外变量。

## 回归测试与验证

原有 RoPE 测试只把 Q/K 输入转换成 BF16，却只对 `RotaryEmbedding` 执行 `.to(device)`，所以测试中的 `inv_freq` 一直是 FP32，没有覆盖真实模型的转换方式。修复后测试直接执行 `.to(device=device, dtype=dtype)`，并断言 `rope.inv_freq.dtype == torch.float32`。

真实权重测试也从固定 4 个 token 扩展为使用默认 chat prompt 连续生成 32 个 token。原问题在第 19 个 token 出现，因此新的测试能够稳定捕获这一回归，同时避免为了单元测试生成数百个 token。

修复后的验证结果如下：

- RoPE 与真实权重定向测试为 `10 passed`。
- 完整测试套件为 `73 passed`。
- 临时恢复 FP32 `inv_freq` 后，本地 BF16 模型与 HF eager 前 300 个生成 token 完全一致。

在 Windows PowerShell 中激活虚拟环境后，使用以下命令再次完成端到端验证：

```powershell
.venv\Scripts\activate
python -m mini_llm.generate
python -m mini_llm.local_generate
```

实际结果如下：

| 项目 | Hugging Face 基线 | 本地模型 |
| --- | --- | --- |
| Prompt token 数 | 35 | 35 |
| 生成 token 数 | 328 | 命令输出 token ID 列表 |
| Prefill 调用 | 1 | 1 次自定义 prefill |
| Decode 调用 | 327 | 逐 token 自定义 decode |
| 停止原因 | `eos` | `eos` |
| 生成开头 | `your lunch plans` | `your lunch plans` |
| 解码文本 | 相同的 10 项午餐建议和结尾 | 与基线一致 |

因此，修复后的结论应表述为：两个入口的生成结果已经一致；`options/choices` 是修复前用于定位问题的分歧，修复后的共同输出为 `plans`。用户粘贴的终端文本中，两边还同时出现了 `suggestions b:`、`lunch opt.` 等截断形式。由于这些片段在两边一致，它们不属于本地模型与 Hugging Face 的对齐问题；如需继续判断是终端复制显示还是实际生成内容，应单独保存完整 token ID 和原始输出进行检查。

未激活虚拟环境时，也可以使用 `uv run python -m mini_llm.generate` 和 `uv run python -m mini_llm.local_generate` 完成同样的验证。

## 可复用的排查方法

生成文本不一致时，直接阅读最终文本通常帮助不大。更有效的方法是把问题按边界逐步缩小：

1. 固定模型 revision、prompt、Tokenizer、dtype、采样参数和 attention backend。
2. 找到第一个不同的 token，并比较该步 top-k logits 和候选间距。
3. 使用相同 token 前缀继续比较，避免输出分叉反过来污染后续诊断。
4. 比较 cached decode 与完整前向，优先排除 KV Cache、position 和 mask。
5. 使用 FP32 重跑。如果 FP32 对齐而 BF16 不对齐，应重点检查常量 dtype、算子顺序和 kernel 差异。
6. 从 Embedding 开始逐层、逐算子比较，定位第一处误差，而不是只观察最终 logits。
7. 将根因转化为最小回归测试，测试必须复现真实运行时的 device 和 dtype 转换方式。

这次问题还说明，`torch.testing.assert_close` 通过并不意味着长序列 greedy token 一定一致。只要 top-1 和 top-2 的间隔足够小，处于容差范围内的数值误差仍可能改变 `argmax`。因此模型正确性测试应同时包含张量容差比较、关键 dtype/shape 不变量以及足够长的 token 级回归。
